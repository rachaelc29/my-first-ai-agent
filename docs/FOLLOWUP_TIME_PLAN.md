# 自然语言跟进时间解析与提醒规则

## 范围

这是阶段 1 后的离线模拟验证，不是阶段 2 语音开发，也不是上线提醒系统。没有飞书连接代码，没有读取真实客户记录、修改字段、发送通知或新增权限。使用 Python 标准库，不需要 AI、依赖安装或付费服务。

现有「下次follow」保持自由文本，是唯一正式计划来源；解析结果只是派生的候选信息，不能覆盖原文。「最新follow」也不改类型。此前只读结构测试确认两者均为文本，但没有验证真实内容或联系日期的含义。

## 可理解的规则

| 表达 | 模拟逻辑 | 提醒保护 |
| --- | --- | --- |
| `2026-12-01`、`2026/12/1`、`2026年12月1日` | 验证真实日历，生成该日候选 | 人工确认后才可使用 |
| `12月初`、`2月1日` | 年份不明 | 不默认为今年或明年，先确认年份 |
| `今年12月初` | 用原始记录日期的年份，窗口 1–10 日 | 确认候选并批准模糊时间规则 |
| `2026年11月中旬` | 窗口 11–20 日 | 默认候选为窗口首日 |
| `2027年2月底`、`月末` | 窗口 21 日至该月末，考虑闰年 | 可改为窗口末日，不偷偷调整 |
| `明年2月` | 原始记录年份加一；整个二月为窗口 | 缺少原始记录日期时暂停 |
| `下周五` | 以记录日期所在周为基准，下一个自然周的周五；周一为周首 | 展示实际日期，避免理解差异 |
| `今天`、`明天`、`后天`、`3天后` | 相对于原始记录日期 | 不是每次扫描的当天，防止计划不断后移 |
| `周五`、`01/02`、`下个月`、其它未支持表达 | 不猜测 | 标记待确认；未来增加规则前先增加测试 |
| `客户回台湾后再联系` | 事件型待办，没有确定日期 | 不生成提醒日期，不能仅靠 AI 判定事件完成 |
| `11月中旬，客户回台湾后再联系` | 时间与事件混合，当前先标记待确认 | 未来确认是两者同时满足、还是仅按日期提前询问 |
| 同一句出现多个时间 | 暂停解析结果 | 先确认哪个日期控制提醒 |
| 已过期计划 | 标记过期待复核 | 不自动补发或跳到下一年 |
| 不存在的日期 | 标记待确认 | 不修成另一个日期 |

上旬/中旬/月底的划分是建议配置，不是已经启用的业务规则。代码当前支持“初、中旬、底、末”；例如“上旬、月底前、约两周”等其他写法仍需确认。第一版刻意保守，未覆盖所有中文表达。

支持时间位于开头，并以逗号、句号、分号或换行与行动文字分隔。没有明确分隔或不符合支持格式时暂停，不截取一句中看起来像日期的文字直接安排提醒。事件识别使用有限关键词，可能误判或漏判；因此所有候选都需要确认，不能把这个原型当成自动理解所有事件的系统。

## 原始记录时间为何重要

相对日期需要知道你是什么时候写下计划。现有「创建时间」是客户档案创建时间，不能默认用作计划记录日期；「最新follow」是文本，也不能假定包含可靠时间。

因此历史相对计划缺少来源日期时必须待确认。未来语音录入会保存输入时的墨尔本时间作为解析基准；相同原文不应因为每日扫描而重新锚定。明确日期不依赖基准。带时区的时间转换到 `Australia/Melbourne` 后取日期，适应夏令时；不接受没有时区的时间戳。

## 跟进原因、目的与行动

目前只把时间之后的内容完整保留为 `action_text`，例如“问候客户，了解孩子学校申请进展”。不拆出未经验证的原因或声称客户有某种事件结果。

后续确认页可将行动拆成原因、联系目的及建议行动供你编辑；涉及 AI 时，生成的总结必须能对照原文，不能补充未经提供的客户事实。阶段 2 再做这部分语义提取和模拟验收，不属于本次原型。

## 提醒安全门槛

输出包含原文、解析基准、时间窗口、候选提醒日、类型和解释。`can_remind` 恒为 false：解析本身不能批准提醒。独立的 `reminder_ready` 演示确认后的日期判定；它不发送消息，不保存确认，也不提供完整去重。

- 时间候选仍需你确认；模糊时间的默认规则也需先批准。
- 只有确认有效、原文仍相同且日期处于窗口内，才可能成为到期待办。
- 候选已过期、条件未明确、原文改变或确认失效时暂停。
- 事件满足也必须由你确认下一次联系日期，本原型不会自动将事件转为今天。
- 可选仅工作日模式会把周末候选移到下周一；若越过窗口边界，必须重新确认。
- 窗口内到期后可生成一条待办，不能天天生成新任务。后续提醒阶段按“客户 ID + 计划版本”去重，保存已通知与完成状态。
- 窗口过期后已存在待办不应悄悄消失；未来调度器保留为逾期待办，由你复核，原型不管理待办生命周期。
- 下一阶段需要持久化用户确认、计划版本/指纹、规则版本、事件确认、通知状态和审计元数据；不把一个布尔参数视为安全身份验证。

## 是否增加辅助字段

暂时不增加任何飞书字段。若以后批准，可考虑同一个多维表格里的辅助字段/辅助规则表：

- 系统提醒日期（日期，只代表确认后的派生日期）；
- 解析状态（待确认、已确认、事件待定、已过期）；
- 计划记录时间（相对日期基准）；
- 系统解析说明/时间窗口；
- 计划版本或确认状态（识别原文变化后使旧确认失效）。

仅“系统提醒日期”一个字段不足以处理事件条件、确认和重复提醒。辅助数据必须能从原计划追溯；原计划编辑后旧派生日期不能继续使用。可先在独立模拟表验证，再由你决定字段名称、位置与权限。如果不希望改表，也可用后端最少任务状态；其内容范围与隐私政策需单独批准，不能形成第二套客户库。

规则管理将来可放在经批准的飞书规则表。现阶段规则对象只是离线模拟配置，没有连接飞书，也没有申请辅助表写入权限。
